# Windows 后台剪贴板高可靠捕获设计

日期：2026-07-12
状态：用户已确认
目标仓库：`Jin-wen-jie/history-clipboard`

## 1. 背景与事实

当前应用只有在 Electron 主进程运行时才能读取剪贴板。现有用户配置中
`launchAtStartup=false`，Windows 登录启动项也不存在，因此电脑重启后若用户没有手动
启动应用，期间的剪贴板变化必然无法记录。

当前分支已经有两项未提交的可靠性改进：每次轮询都读取文本和图片，从而覆盖纯图片
变化；历史元数据写入改为串行可等待，从而消除 `addText()` 返回后 200ms 内重启导致的
丢失窗口。这些改动仍不能解决进程未运行、助手异常退出、快速连续变化和正常退出时队列
未排空的问题。

此前的 C# 监听助手曾因异常退出后无人重启而长期失效。`WM_CLIPBOARDUPDATE` 本身只
通知“内容发生变化”，不携带对应版本的序列号或内容快照；如果助手只发送通知，再由
Electron 读取当前剪贴板，高速 A -> B -> C 仍可能只读到 C。因此增强方案必须让助手在
处理 Windows 消息时尽快复制内容，并由主进程监督助手健康状态。

## 2. 目标

1. Windows 用户登录后，应用自动静默进入托盘，无需打开主窗口即可持续记录。
2. 用户手动启动应用时始终显示主窗口；关闭窗口只隐藏到托盘。
3. 原生助手在剪贴板变化后尽快抓取文本和图片快照，降低 200ms 轮询带来的采样遗漏。
4. 助手异常退出或挂起时自动降级到轮询并重启，不再静默失效。
5. 相同内容的重复复制也作为合法事件处理，更新已有记录的时间和复制次数。
6. 正常退出前排空捕获和持久化队列；异常中断后元数据仍保持为可恢复的完整版本。
7. 敏感内容过滤默认关闭且在设置页可见，避免无提示地遗漏验证码、密码或 Token。
8. 在当前电脑完成数据备份、升级和验收，并将源码与 `0.1.1` 安装包发布到 GitHub。

## 3. 非目标与可靠性边界

- 不尝试读取或反向解析 Windows 系统剪贴板历史。
- 不使用 Windows 服务。服务位于 Session 0，不能可靠访问当前交互用户会话的剪贴板。
- 不记录文件复制列表，不增加图片 OCR，不增加云同步。
- 不承诺绝对零遗漏。进程离线、系统消息尚未调度内容就被再次覆盖、剪贴板所有者长期
  占锁或延迟渲染失败时，Windows 没有可供应用回放的旧状态。
- 可承诺的范围是：应用与助手在线且能在内容被再次覆盖前取得剪贴板锁时，近实时保存
  文本和图片；所有已检测到的缺口都必须可见，不得静默失败。

## 4. 用户行为

### 4.1 登录与手动启动

- 登录启动项固定使用当前打包程序路径和 `--launch-at-login` 参数。
- 只有带该参数的首次实例静默启动；普通快捷方式、开始菜单和双击启动均显示主窗口。
- 已静默运行时，用户再次手动启动会通过单实例事件显示并聚焦现有窗口。
- 从托盘主动选择“退出”后，本次登录会话保持退出，不启动监督器，也不自动拉起主进程。

### 4.2 新安装与升级迁移

设置持久化新增 `startupDecisionVersion`，当前决策版本为 `1`。

- 全新安装：`launchAtStartup=true`、`startupDecisionVersion=1`，首次运行即注册登录项。
- 旧版已开启：保留开启，重写为带 `--launch-at-login` 参数的新登录项，并记录决策版本。
- 旧版关闭或字段缺失：保持关闭并显示一次“启用后台记录 / 暂不启用”的明确提示。
- 用户选择后写入决策版本；选择关闭后，后续升级不得擅自重新开启。
- 提示出现时退出应用则保持待决定状态，下次启动继续提示。
- 设置文件损坏但存在 `history.json`、`vault.key` 或内容目录时，按旧用户处理，不能误判为
  全新安装并静默开启。
- 开发模式不注册登录项，避免把 `electron.exe` 写入 Windows 启动项。

`launchAtStartup` 表示用户期望，Windows 实际注册状态单独查询。注册或注销失败时保留用户
期望以便下次重试，同时在设置页显示“启动项异常”，不能用配置布尔值假装系统操作成功。
注册、注销和查询必须使用同一组 `path` 与 `args`，迁移时移除旧的无参数登录项。

### 4.3 敏感过滤

- 全新安装和本次旧版迁移都将 `sensitiveFilterEnabled` 设为 `false`。
- 设置页提供明确开关，用户可随时主动开启。
- 过滤开启时，被拒绝内容只记录计数和原因，不记录正文；相同内容不会每 200ms 重复处理。
- 用户关闭过滤后立即对账当前剪贴板；若被过滤内容仍是当前值，则允许正常保存。

## 5. 总体架构

```text
Windows WM_CLIPBOARDUPDATE
        |
        v
C# Clipboard Agent
  - 同一用户会话中的隐藏消息窗口
  - 立即复制文本/图片到内存
  - 有界内存队列与心跳
        |
        | 版本化二进制 stdout 帧
        v
Clipboard Agent Supervisor
  - READY 握手、心跳、代次隔离
  - 异常重启与轮询降级
        |
        v
Clipboard Capture Queue
  - 原生事件按序处理
  - 兜底轮询按内容去重
        |
        v
HistoryStore
  - 内容加密
  - 串行、原子元数据写入
```

## 6. 原生快照助手

### 6.1 技术选择

助手使用极小的 C#/.NET Framework WinForms 可执行文件：

- Windows 自带的 .NET Framework 4.x 编译器足以构建，不新增 Node 原生 ABI 依赖。
- 独立进程发生异常时不会带崩 Electron 主进程。
- GitHub `windows-latest` 可直接构建，安装包只额外携带助手 EXE，不捆绑完整运行时。
- 不采用 `clipboard-event`：该包最后发布于 2022 年，Windows 实现同样是无人监督的 C#
  子进程，且没有可靠的分片解析、心跳或重启机制。
- 不采用 Node 原生 addon：会引入 Electron ABI/rebuild 风险，原生崩溃还会直接结束主进程。
- 不采用 Rust helper：当前本机没有 Rust 工具链，收益不足以覆盖新增构建和双语言维护成本。

### 6.2 消息与快照

- 助手在 STA 消息线程创建隐藏窗口，并调用 `AddClipboardFormatListener`。
- 收到 `WM_CLIPBOARDUPDATE` 后立即尝试打开剪贴板，在同一次打开/关闭周期内复制可用的
  Unicode 文本和图片数据。
- 图片格式优先使用剪贴板中的 PNG，其次兼容 DIB/DIBV5/位图，并在助手内转换成 PNG。
- 打开剪贴板失败时采用有限退避，总重试预算不超过 1 秒。
- 若重试期间序列号已经前进，旧状态视为不可恢复，助手发出 `gap`，然后捕获最新状态。
- `GetClipboardSequenceNumber` 只用于发现变化和潜在缺口，不作为精确事件 ID，也不作为
  唯一的内容去重键。
- 消息线程只负责复制快照并放入内存队列；独立 writer 线程负责管道输出，避免大图片阻塞
  Windows 消息循环。

### 6.3 助手内存边界

- 待发送队列上限为 64 帧且总负载不超过 64 MiB，两项任一达到即执行背压处理。
- 单个快照超过 64 MiB 时不发送正文，只发送 `too-large` 错误帧。
- 队列溢出时丢弃最旧的未发送快照、保留最新快照，并在下一个快照前发送包含丢弃数量的
  `gap/overflow` 控制帧；任何丢弃都不得静默发生。
- 父进程管道关闭、stdin EOF 或收到 `SHUTDOWN` 后，助手注销监听器并退出，避免孤立进程。

## 7. 进程协议

stdout 使用版本化长度前缀二进制帧，禁止用逐行 JSON 承载图片：

```text
[frameLength:u32le][headerLength:u32le][header:utf8-json][payload:bytes]
```

- `frameLength` 是其后全部字节数；`headerLength` 只计算 JSON 头长度。
- 协议版本从 `1` 开始。
- 帧类型包括 `ready`、`snapshot`、`heartbeat`、`gap` 和 `error`。
- `snapshot` 头包含序列号、捕获时间、文本/PNG 分段偏移与长度、图片宽高。
- payload 按头部声明顺序拼接 UTF-8 文本和原始 PNG，不使用 Base64，避免约 33% 膨胀。
- parser 最大接受 64 MiB；长度非法、JSON 非法或分段越界都视为协议损坏并重启助手。
- stderr 仅用于诊断，不得输出文本、图片字节、哈希前原文或其他敏感内容。
- stdin 接受简单的 `PING` 与 `SHUTDOWN` 控制命令；EOF 也等价于停止。

## 8. 助手监督器

监督状态为 `stopped -> starting -> running -> backoff`，正常退出另经 `stopping`。

- 每次 spawn 分配递增 `generation`；旧 generation 的迟到数据和退出事件必须忽略。
- 3 秒内未收到合法 `ready` 即判定启动失败。
- 助手每 5 秒发送心跳；15 秒没有心跳即判定挂起，终止后重启。
- `error`、`close`、stdout 结束和握手超时通过同一个 failure gate 处理，避免重复重启。
- 退避为 0.5、1、2、4、8、16、30 秒，带约 20% jitter；连续健康 60 秒后重置。
- 首次 READY、系统睡眠恢复和每次重启 READY 后都强制对账当前剪贴板。
- 助手健康时不固定读取剪贴板正文；每 5 秒心跳携带当前 sequence，与最后已处理 sequence
  不一致时才触发一次快照对账并记录 gap。助手异常时立即切换到 200ms 全量轮询。
- 对账轮询按内容去重；原生 `snapshot` 不按内容去重，因此相同内容的重复复制仍会更新记录。
- 只有轮询任务允许因已有轮询待处理而合并；原生事件不能沿用当前 `pending > 10` 的静默
  跳过逻辑。
- 主动退出先把 `desiredRunning` 设为 false 并取消所有重启定时器，再关闭助手；其退出事件
  不能触发重新拉起。

监督器向渲染进程暴露不含内容的健康状态：阶段、助手 PID、最后事件时间、最后序列号、
重启次数、下一次重启时间、缺口数、队列深度和最后错误类型。

## 9. 捕获队列与存储

### 9.1 捕获队列

- TypeScript parser 在收到完整帧后立即复制出独立 Buffer，再交给单消费者 Promise 队列。
- 队列按助手帧顺序处理；图片和文本属于同一个快照，但继续作为两条历史内容保存。
- Electron 使用收到的完整 PNG 生成现有 `ImageInput` 所需缩略图，助手不重复传输缩略图。
- 父进程队列达到高水位时暂停读取 stdout，让 OS 管道和助手队列自然形成背压；降到低水位
  后恢复读取。
- 原生快照即使内容哈希相同也调用 HistoryStore，由存储层更新 `updatedAt` 和 `copyCount`。
- 轮询路径继续使用内容哈希去重，避免 sequence 异常对账和 200ms 降级轮询重复计数。

### 9.2 原子持久化

- 所有元数据写入挂到同一 Promise 链，调用方等待本次 revision 真正落盘。
- 每次写入在相同目录创建临时文件，完整写入并同步后，以替换方式更新 `history.json`。
- 元数据增加单调递增的 `revision`；主文件、临时文件和备份都通过结构校验后按 revision 选择。
- 替换前保留上一份已验证主文件为 `.bak`；启动时依次验证主文件、临时文件和备份文件，
  选择最新的完整版本恢复。
- 新增内容时先完成加密内容文件，再提交引用它的元数据。
- 删除内容时先提交不再引用它的元数据，再删除加密内容文件。
- 启动时清理未被元数据引用的孤立加密文件和过期临时文件。
- `HistoryStore.flush()` 等待当前写入链；写入失败向调用方传播，同时保留可继续使用的链。

### 9.3 正常退出

首次 `before-quit` 执行以下顺序并阻止立即退出：

1. 标记应用正在退出，停止产生新事件。
2. 停止助手监督器并关闭助手。
3. 停止健康对账和降级轮询。
4. `await watcher.drain()`。
5. `await store.flush()`。
6. 注销全局快捷键，标记排空完成，再次调用 `app.quit()`。

后续 `before-quit` 不再阻止，保证退出流程只执行一次。

## 10. UI 与 IPC

### 10.1 专用启动项接口

通用 `settings:update` 不再直接修改 Windows 登录项。新增专用接口：

- `startup:getState`：返回用户期望、Windows 实际状态、是否待询问和错误类型。
- `startup:setEnabled(enabled)`：写入用户选择和决策版本，注册/注销登录项，再查询实际状态。

设置页开关显示用户期望，同时用状态文本反映实际结果。失败时显示错误提示并允许重试。

### 10.2 后台状态

设置页显示以下互斥状态：

- `正常监听`：助手健康，事件模式工作中。
- `轮询降级`：助手异常，200ms 轮询工作中并等待重启。
- `已暂停`：用户关闭捕获。
- `启动项异常`：期望与 Windows 实际注册状态不一致。

状态 UI 只显示计数和错误类型，不展示剪贴板内容。敏感过滤使用现有二元开关样式。

## 11. 错误处理

| 故障 | 行为 |
|---|---|
| 助手文件缺失或无法启动 | 应用继续运行，进入 200ms 轮询并显示降级状态 |
| READY 超时、异常退出或心跳丢失 | 终止旧 generation，退避重启，轮询不中断 |
| 剪贴板被占用 | 助手有限重试；超时后发 gap/error，并对账最新内容 |
| 协议帧损坏 | 丢弃该 generation，记录协议错误并重启助手 |
| 队列内存超限 | 背压；助手必要时丢最旧项、保最新项并显式报告 gap |
| 元数据写入失败 | 当前操作失败，保留上一完整版本，后续写入链仍可继续 |
| 主元数据损坏 | 从最新有效临时文件或 `.bak` 恢复 |
| 登录项注册失败 | 保存用户期望、显示实际失败并在后续启动重试 |
| 用户主动托盘退出 | 排空队列并退出，不启动任何自动重启 |

## 12. 安全与隐私

- 剪贴板正文只存在于剪贴板、助手内存、本机匿名管道、Electron 内存和加密内容文件中。
- 助手不得创建明文快照文件；图片也通过二进制管道传输。
- 日志禁止包含正文、图片、Base64、可逆片段或原始文件路径。
- 备份用户数据时只复制加密内容、密钥文件和元数据，并用文件数及 SHA-256 清单校验；
  验证过程不解密正文。
- 保持 `contextIsolation=true` 和 `nodeIntegration=false`，渲染进程只能通过明确 IPC 读取状态。
- 原生助手只接受父进程 stdin 控制，不开放网络端口或全局命名管道。

## 13. 测试设计

### 13.1 单元测试

- 二进制 parser：同 chunk 多帧、跨 chunk、残缺头、非法长度、非法 JSON、分段越界、64 MiB
  上限和旧 generation 数据。
- 监督器：READY 超时、spawn error、error+close 只处理一次、心跳超时、退避递增/封顶、
  健康 60 秒后复位、各状态 stop、迟到事件和主动退出不重启。
- 序列与缺口：重复序列、前进、跳号、重启期间缺口和 uint32 回绕。
- 捕获队列：A/B 在 A 持久化阻塞时仍按序保存、重复内容的两个原生事件都处理、轮询不重复。
- 存储：调用返回前可被新实例读取、临时文件原子恢复、备份恢复、写入失败后链可继续、
  `flush()` 等待最后 revision。
- 迁移：全新目录、旧版 false、旧版 true、明确关闭、损坏设置、设置缺失但历史数据存在。
- UI：升级提示两个选择、登录项实际状态、过滤开关和四种后台状态。

### 13.2 Windows 集成验收

1. 连续 3 轮写入 20 个唯一文本，间隔 100ms，每轮全部进入历史。
2. 连续复制相同文本两次，记录不重复创建，但 `copyCount` 和更新时间增加。
3. 文本为空时连续复制两张不同图片，两张都保存且缩略图可读。
4. 人为占用剪贴板后复制，验证有限重试、缺口状态和恢复后的最新内容对账。
5. 强制结束助手，验证 15 秒内识别异常、轮询继续工作且助手按退避自动恢复。
6. 模拟助手输出损坏帧和超限帧，验证主进程不中断且进入重启流程。
7. 退出前立即复制，验证最后事件在退出完成前落盘。
8. 在元数据替换阶段中断进程，重启后主文件、临时文件或备份至少有一个可恢复版本。
9. 登录参数启动时不显示窗口；普通启动显示窗口；关闭窗口后继续捕获。
10. 托盘主动退出后助手与主进程都结束，且本次会话不自行重启。
11. 扫描应用日志和临时目录，确认没有测试文本或图片字节的明文副本。

完整验证命令至少包括：

```bash
npm test
npm run build
npm run dist
```

安装包还必须检查 `resources/clipboard-listener.exe` 存在并能完成 READY 握手。

## 15. 成功标准

- 用户登录后无需打开窗口即可记录，手动打开仍能看到主界面。

- 受控 100ms 连续文本验收、纯图片验收和相同内容重复复制验收全部通过。

- 新安装、旧用户升级、明确关闭和设置损坏四类启动迁移行为符合本设计。
- 敏感过滤默认关闭且可由用户控制。
- 本机升级后历史数据完整，`npm test`、`npm run build`、`npm run dist` 全部成功。
